# TeaseScript AI development workflow context

**Purpose:** Stable routing context for connector-local ChatGPT sessions.
**Authority:** GitHub is canonical. The verified checkout's `AGENTS.md`,
`docs/DEVELOPMENT-WORKFLOW.md`, and focused capability guide control the exact
current process.

## Default implementation workflow

Use one coherent issue, one owning agent, one short-lived branch, one pull
request, independent review, CI, squash merge, and branch deletion by default.
A preselected batch of small related issues is acceptable only when the combined
implementation and review are simpler and the pull request lists every included
issue explicitly.

The implementing agent reads the smallest authoritative source set, states the
expected files, acceptance criteria, and risks, works in verifiable increments,
updates directly affected documentation, and keeps the pull-request description
aligned with the actual result.

## Connector-local source and execution route

For substantial work:

1. resolve and download one exact verified source artifact through the current repository connector workflow;
2. use the stable `teasescript-agent-bootstrap-linux-x64.tar.zst` package;
3. run its sole normal entry point, `bin/prepare-agent-workspace.sh`;
4. inspect, edit, test, and review locally;
5. return to the connector only for live GitHub state and GitHub writes.

Do not attempt network Git, read the repository file by file, invent another
bootstrap self-test, or execute the candidate copy of source-preparation tooling
from the artifact under review. Read `LOCAL-AGENT-BOOTSTRAP.md` for the compact
command route and the repository's `docs/CHATGPT-GITHUB-WORKFLOW.md` for current
artifact acquisition details.

## Publication route

Immediately before a repository-content or ref write, classify the action:

- normal authenticated Git branch/commit/push; or
- verified patch publication through `docs/PATCH-PUBLICATION.md` because normal push is unavailable.

Do not use low-level blob, tree, commit, branch, or full-file connector actions
as an ad hoc source publication route. In verified patch publication, use only
the exact next action generated by the repository helper for the declared
`.agent-patch-publication/` transfer payload. Do not Base64-wrap ordinary UTF-8
patch text or substitute complete changed files.

## Ownership and coordination

The product owner decides product scope, priorities, gates, and unresolved
product or architecture choices. A designated coordinator may sequence work,
resolve dependencies, and review cross-issue consistency. Ordinary issues do
not require an integration branch or coordinator-controlled implementation.

Temporary work breakdowns and chat notes remain outside GitHub. Accepted
outcomes and implemented behavior must be synchronized into the applicable
canonical repository owners.

## Shared-project synchronization

The repository owns the maintainable shared routing sources and staging helper.
The shared project is a controlled derivative, not a second editable workflow
owner. Generate a fresh exact replacement set, remove suffixed/versioned current
copies from the project folder, upload the stable replacements, and record that
manual synchronization. Do not restore the retired work-package workflow or
invent a replacement handoff system.
